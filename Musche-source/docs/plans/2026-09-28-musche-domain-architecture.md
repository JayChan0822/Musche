# Musche 业务架构梳理

状态：业务设计草案；尚未实施数据迁移或业务代码重构。
日期：2026-09-28。

## 1. 已确认的业务基础

- 项目通常就是一首曲目，例如《送情郎》。当前不增加独立的“曲目”实体。
- 项目下的某个乐器/声部是一项基础任务，例如“送情郎 · 二胡”。
- 同一项任务分别需要 REC（录音）和 EDIT（剪辑）。
- REC 分配给演奏员；EDIT 分配给剪辑员。两项工作共享任务身份，但负责人、排期、进度和耗时分别记录。
- 项目不会因负责人不同而变成另一个项目。“REC 项目 / EDIT 项目”应理解为同一项目的两种工作阶段。

## 2. 目标关系

```text
项目：送情郎
├─ 基础任务：二胡声部，内容时长 3:00
│  ├─ REC 工作 → 演奏员 A → 排期 → 录音工作记录
│  └─ EDIT 工作 → 剪辑员 B → 排期 → 剪辑工作记录
└─ 基础任务：古筝声部，内容时长 1:30
   ├─ REC 工作 → 演奏员 C → 排期 → 录音工作记录
   └─ EDIT 工作 → 剪辑员 B → 排期 → 剪辑工作记录
```

基础任务可以先创建、后分配。未选择演奏员或剪辑员不妨碍保存任务。

## 3. 业务对象及边界

| 对象 | 作用 | 主要信息 | 不应放入的信息 |
|---|---|---|---|
| 项目 Project | 一首曲目的业务归属 | 名称、颜色、项目资料、MIDI 来源 | 用于判定 REC/EDIT 的标记 |
| 乐器 Instrument | 全局乐器资料 | 名称、家族/分组、颜色 | 某个项目的演奏时长 |
| 人员 Person | 一个真实人员及其可承担角色 | 名称、角色列表、颜色 | 手填的“个人平均倍率” |
| 基础任务 Task | 项目中的一个乐器/声部 | projectId、instrumentId、声部名称、内容时长 | 只能用于 REC 的固定负责人 |
| 阶段工作 StageWork | 基础任务的一道工序 | taskId、stage=rec/edit、负责人、预估耗时、工作状态 | 用 projectId 是否存在推断阶段 |
| 工作分段 WorkPart | 某一阶段的内容分工 | stageWorkId、内容范围/时长、完成状态 | 自动复制到另一阶段的拆分结果 |
| 排期时间块 ScheduleBlock | 在日历上占用的时间 | stage、开始/结束、人员、场地、计划容器 | 基础任务身份和实际完成量 |
| 排期明细 ScheduleAllocation | 时间块内具体安排的工作 | blockId、workPartId、排序、可选分配分钟数 | 用排序序号充当永久关联 |
| 工作记录 WorkLog | 实际完成的工作及耗时 | workPartId、可选 blockId、实际人员、日期、耗时、休息、成果 | 把整块时长完整复制到每个任务 |
| 日程计划 PlanningBoard | 当前“新建日程”的组织容器 | 名称、排期与阶段工作的归属/筛选 | 一次录音场次本身 |

以上是业务实体，不等于每个实体都要成为独立页面，也不要求立刻拆成服务。

### 任务身份

默认按“项目＋乐器”创建任务，但始终使用独立 taskId，不设置全局的 projectId＋instrumentId 唯一约束。
同一项目允许“小提琴一部 / 二部”“钢琴左手 / 右手”等多个声部。重复导入应提供更新或新建的明确策略。

### 人员及角色

建议全局人员库支持 musician、editor、engineer、operator、assistant 等角色。同一个人可以同时演奏和剪辑。
录音棚是场所资源，不能和人员合成一种对象。

首期每项阶段工作有一个主要负责人；多人合作可记录参与者。真正把工作分给多人时，应明确各自负责的分段，不能只追加名字。
改变当前负责人不改写历史工作记录中的实际人员。

## 4. REC/EDIT 与界面分组彻底分离

两个相互独立的选择：

- 工作阶段：REC / EDIT。
- 浏览分组：按负责人 / 项目 / 乐器。

REC 默认按演奏员分组，EDIT 默认按剪辑员分组。同一个项目、乐器和人员可以在两个阶段下分别统计。
切换视图只改变展示，不改写任务字段、负责人或工作时长。

推荐界面：

- 左侧：REC/EDIT 切换，阶段工作列表，待分配入口，分组和筛选。
- 中间：所选阶段的排期；时间块显示负责人，内部列出关联项目和任务。
- 右侧：项目、乐器、人员资料；人员可按角色筛选；录音棚等辅助资料保留次级入口。
- 项目详情：每个乐器任务同时展示 REC 与 EDIT 的负责人和进度。
- 人员/乐器/项目详情：阶段过滤后展示对应历史、倍率和工作量。

## 5. 分配、排期、实际记录是三件不同的事

以“送情郎 · 二胡”为例：

1. 创建任务，内容时长 3:00，生成 REC 和 EDIT 工作。
2. REC 负责人选 A，EDIT 负责人选 B。此时可以均未排期。
3. 把 A 的录音安排在周一 10:00–11:00；把 B 的剪辑安排在周二 14:00–14:30。
4. A 实际录音耗时 45 分钟，完成全部 3 分钟内容；REC 完成，EDIT 不因此完成。
5. B 实际剪辑耗时 24 分钟，完成全部 3 分钟内容；EDIT 完成。
6. REC 实际倍率为 ×15；EDIT 实际倍率为 ×8。最初的安排倍率分别为 ×20、×10。

允许先分配剪辑员、预排剪辑时间，不强制整项 REC 完成后才能做这些操作。
是否阻止剪辑尚未录好的分段属于后续可配置的依赖规则；首期建议提示可用录音范围，而不是硬锁整个项目。

## 6. 拆分和重录

- REC 与 EDIT 各自拥有分段。录音分两次，剪辑可以一次完成；二者不必一一对应。
- 分段归属于阶段工作，而不是复制一个新的项目或乐器任务。
- 首期可以使用稳定的分段 ID＋内容时长；若没有小节/时间范围，不显示伪精确的区间覆盖率。
- 新模型支持多次工作记录：同一段重录两次，累计两次耗时，但已完成内容只算一次。
- 已完成内容通过分段完成信息或实际范围并集计算，不能累加每次工作记录的内容长度。
- 核心身份与历史内容版本需稳定。MIDI 重新导入改变时长时，不能静默改变历史倍率的分母；已有记录保留当时的内容范围/时长快照。
- 老数据只有“分段时长”时保留该精度，不反推不存在的时间轴位置。

## 7. 状态拆分

避免一个字段同时代表负责人、排期充足程度和录制进度：

| 状态维度 | 示例 | 判断依据 |
|---|---|---|
| 分配状态 | 待分配 / 已分配 | 阶段工作是否有负责人 |
| 工作状态 | 未开始 / 进行中 / 已完成 / 不需要 | 对应阶段的完成范围和显式状态 |
| 排期状态 | 未排 / 已排 | 是否有关联时间块 |
| 时间余量 | 待评估 / 偏紧 / 充足 | 安排时长与有效预估基准的对照 |

“有实际耗时”不自动等于“完成”；可能只录了部分或正在返工。
“已排”不自动等于“时间充足”。没有有效估算依据时不显示“缺时”。
REC 完成不自动改写 EDIT 完成状态。

## 8. 时间字段和唯一来源

| 时间 | 来源 | 编辑影响 |
|---|---|---|
| 内容时长 | 基础任务及内容版本 | 更新未来工作量，历史记录保留快照 |
| 预估工作耗时 | 阶段工作的预估值 | 可重新预估，但不能覆盖已确认的排期或实际记录 |
| 计划时间 | 排期块 startAt/endAt | 拖动改变排期；不改写平均倍率或历史耗时 |
| 实际工作时间 | 工作记录的起止时间或手填净耗时 | 更新实际统计，不默认覆盖原计划 |
| 中断时间 | 工作记录明确记录的休息 | 起止计算时扣一次，手填净耗时时不再次扣减 |

时间戳包含日期和时区，支持跨午夜；避免只存 HH:MM 后再从当前排期猜历史日期。
数值采用秒；HH:MM:SS 仅用于输入输出和显示。

排期块实际场次时长与任务实际耗时是不同层级。不能把“场次实耗＋场内任务实耗”相加。
只有整个场次耗时、没有任务分摊时，展示为场次统计；不生成虚假的乐器/项目单项实耗。

## 9. 倍率与统计

### 实际倍率

在明确范围内：某阶段实际工作耗时之和 ÷ 对应内容时长之和。

- REC 只读 REC 工作记录，EDIT 只读 EDIT 工作记录。
- 人员、项目、乐器只是汇总维度，不再决定记录类型。
- 同一内容重复尝试的耗时累加；对应内容范围去重，避免把返工成本掩盖掉。
- 多人合作分别统计个人工时；场次历时单独统计，不能把两人同时工作一小时解释成场次持续两小时。
- 展示样本数量、中位数与数据范围；缺失实际耗时或内容依据的记录不参与倍率。
- 历史平均是计算结果，不是可手填的人员默认属性。

### 安排倍率

某阶段安排时间 ÷ 对应安排的内容时长，内容按范围去重。
一个时间块包含多个任务时：

- 负责人总体安排倍率可以对整块及对应内容计算。
- 想展示其中一个乐器/项目的安排倍率，需要先有排期明细的分钟分配；否则显示“未分配”，不能把整块时间重复计入每项任务。

### 初始预估

建议依次参考：同阶段＋同人员＋同乐器的有效历史 → 同阶段同人员的历史 → 人工填写预计耗时。
样本不足必须标注。无历史数据时可允许用户显式采用系统参考值，但不能在界面隐藏一个 ×20 并据此判断缺时。
实际倍率变化只更新建议，不自动挪动已确认日程。

## 10. 冲突规则

以实际占用的人和资源判断冲突，不按 REC/EDIT 两个大类一刀切：

- 同一个人在同一时段被安排两份工作，需要冲突提示；即使一份 REC、一份 EDIT。
- 同一录音棚有排他占用时，需要冲突提示。
- 不同人员、不同资源可以并行；同项目或同乐器本身不等于冲突。
- 未分配负责人时，允许形成待定安排，但标为无法完成个人冲突检查。
- 建议对生效日程计划进行跨计划检查。若存在相互替代的方案，必须标记为备选，避免把备选方案当作实际占用。

## 11. Session / 日程计划

现在的 sessionId 是任务集合的隔离容器，不是一次录音场次。
建议产品继续称“日程”，内部明确为 PlanningBoard，避免与 ScheduleBlock 混淆。

- 项目、乐器、人员是全局资料。
- 基础任务是项目内容，可被不同计划中的阶段工作引用。
- 首期迁移保留旧日程隔离，不自动跨日程合并同名任务。
- 计划移除、跨计划复制与归档需要明确动作，不能因为删除容器而留下无法访问的数据。
- 同一内容的 REC 和 EDIT 可分配到不同计划，但这应是显式操作。

## 12. Metadata 的位置

- 场所使用 studioId 引用。
- 工程师、操作员、助理是人员在具体工作/场次中的参与角色，以 personId 引用。
- 剪辑员是 EDIT 的负责人，不从“操作员”字段自动推断。
- 资料名称用于显示，关联以 ID 为准；改名不会让历史统计失联。
- 历史署名可另外保留名字快照，不需要为了维护关联而批量替换所有字符串。
- 现有“甲 / 乙”这种联合姓名条目不自动拆成两个人，也不与其他同名资料自动合并。

## 13. 现有实现与迁移方向

| 现有实现 | 目标方向 | 迁移注意事项 |
|---|---|---|
| itemPool 一条记录包含 projectId/instrumentId/musicianId | 基础任务＋REC/EDIT 阶段工作 | 演奏员只作为 REC 分配；任务能未分配 |
| sidebarTab = musician/project | stage = rec/edit ＋ groupBy | 切阶段不再等于换分组 |
| records.musician | REC 实际记录 | 保留缺失信息及来源 |
| records.project | EDIT 实际记录 | 剪辑员未记录则保持未知 |
| records.instrument | 待审查遗留记录 | 未明确其含义前不映射、不删除 |
| splitViews.musician/project | REC/EDIT 的独立工作分段 | 保留两套拆分结构和工作量 |
| 根/子拆分条目 | 原任务＋阶段分段 | 以 splitFromId 图和共同身份验证归并，不能只按名字 |
| sectionIndex | blockId/workPartId 的显式排期明细 | 按旧顺序推断后保留映射报告；不确定项待确认 |
| scheduledTasks / templateId | 时间块＋排期明细 | 保留单任务块和聚合块；所有外键重新映射 |
| ratio / ratios / defaultRatio | 历史派生统计＋阶段预估 | 实际历史不被旧默认值污染；保留旧预估便于核对 |
| recordingInfo / editInfo 字符串 | 按阶段和参与角色关联 ID | 名称重合不代表同一个人；歧义人工处理 |
| project.midiData[instrumentId] | 任务内容来源及版本 | 同乐器多声部不自动合并 |
| v9_data / 云端 JSON | 带 schemaVersion 的新快照 | 浏览器、云端、导入导出、iOS 同时考虑版本兼容 |

源代码依据：
- `app/scripts/features/quick-add.js`：任务创建必须指定 musicianId。
- `app/scripts/utils/sidebar-tabs.js`：REC/EDIT 对应 musician/project。
- `app/scripts/utils/split-state.js`：阶段数据按视图名称组织，存在与顶层字段同步。
- `app/scripts/features/schedule-drag-drop.js`：聚合块依视图设置身份字段。
- `app/scripts/features/schedule.js`：冲突类型依项目/乐器字段推断。
- `app/scripts/features/track-list-records.js`：阶段记录与场次总耗时并存，修改记录可回写排期。
- `app/scripts/features/session.js`：session 是“新建日程”容器。
- `app/scripts/features/data-autosave.js`：pool/tasks/settings 统一快照保存。

## 14. 分步重构建议

1. 冻结业务口径，导出原始备份；引入 schemaVersion 和可回退迁移工具。
2. 引入 REC/EDIT 阶段及独立负责人；先以兼容读取层维持当前 UI，不在各组件重复判断旧字段。
3. 提取基础任务、阶段工作、分段、明确的排期关联和实际记录；新写入只使用新模型。
4. REC/EDIT 切换与分组解耦；补待分配、剪辑员分配和阶段进度。
5. 统一冲突、倍率、项目/人员/乐器详情统计；然后同步导入导出、自动保存和 iOS。
6. 迁移核验完成后才删除旧字段兼容逻辑。禁止新旧两套数据长期互相覆盖。

前端 Vue、左右栏、时间轴、拖拽交互、对话框以及现有大部分样式可以保留。
主要重构领域模型、数据访问/操作层和统计，再让视图读取结果；暂不拆微服务或为概念模型引入新的后端技术。

## 15. 重构验收例子

- 不选任何负责人，也能创建“送情郎 · 二胡”。
- 给 REC 选 A、给 EDIT 选 B，切换视图不改变双方分配。
- A 完成录音后，B 的剪辑仍然待完成。
- REC 拆两段，EDIT 不强制拆两段；两阶段总内容仍归属同一任务。
- A 周一同一时段既录音又剪辑会报冲突；A 和 C 在不同场所并行录音不因为都属于 REC 而被阻止。
- 拖动或缩放排期，只改变计划；撤销可以恢复，不污染实际倍率。
- 整场录音耗时未按任务分配时，单乐器统计不重复加整场耗时。
- 工作记录换人后保留历史执行人；资料改名后历史关联仍存在。
- 没有实际记录不显示实测平均倍率；有耗时但未完成不直接标完成。
- 迁移前后各阶段内容总时长、实际耗时、跳过项、拆分关系和排期数量可核对；无法确认的负责人/日期不猜测。

## 16. 后续需要确认的边界

这些不阻碍以上基础设计，实施前再按真实使用场景确认：

1. 重录、返工是否需要独立轮次，以及如何标记完成内容。
2. 多人合奏是按个人声部分任务，还是一项任务保留完整编制和参与名单。
3. 当前“日程”是否包含相互替代的排期方案，决定跨日程冲突检测范围。
4. EDIT 可用内容如何确认：仅看 REC 完成状态，还是记录实际交付素材。

首期建议使用最小可用规则：单个主要负责人、两个独立阶段、阶段内分段、显式时间块关联、可靠的实际工作记录。
